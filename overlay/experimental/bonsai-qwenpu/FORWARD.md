# Bonsai with QwenPU in the decoder

The forward checkpoint extends the Qwen3.5 decoder used by Bonsai 27B. One `llama_decode` call builds a GGML graph with 23 CUDA-backed nodes for the compiled QwenPU circuit's projection and recurrent sublayers. A final GPU node selects the circuit coordinates retained across the language stack. Bonsai's packed token embedding lookup, language layers and output head run on the same GPU.

Each text token supplies both its original Bonsai embedding and its circuit features. The host assembles the circuit features from the packed token table and uploads the input row. Bonsai's layer weights, language embedding and separate output head keep their original GGUF types, dimensions and bytes. The upstream layout gives a logical residual width of 7,680 after live-slot allocation. The executor works on a separate sparse circuit representation with 6,914 IR coordinates, then projects the circuit output to the code, tau and mu lanes retained by that layout. These lanes contribute their squared magnitude to each full-residual RMS norm in Bonsai. With language width `D` and logical width `W`, the denominator in the original language coordinates is `sqrt((sum(text²) + sum(kept²)) / D + eps * W / D)`. The learned norm weights multiply the normalized language coordinates as usual.

The host reads back the small set of retained coordinates and decodes the signed circuit output as a model token ID when tau is zero. Private chip IDs begin after the original vocabulary and take the chip-only form of the same decoder graph. These calls advance circuit state without touching Bonsai's position, attention cache or recurrent memory. A circuit-selected language token goes through the full decoder at the next text position. When tau gives ownership back to Bonsai, the caller uses its language logits. `llama_qwenpu_forward_get` exposes the selected token or `-1` for language sampling, the last text position, the retained residual norm and the actual CUDA layer launch count.

See [the reproduction guide](../../../docs/REPRODUCE.md) for the pinned inputs, Windows build, vector fixture, and one- and three-token stories260K runs.

The preparation script builds the overlay at Prism revision `9fcaed763ccda38ea81068ad9d7f991aaddca451`. It uses the Windows C++ and NVRTC toolchain, imports the installed GGML DLLs, and places the candidate and its CUDA module under `dist/local-bench/bonsai-forward/candidate`. The vector fixture GGUF contains a parked firmware snapshot. The separate story GGUF contains two snapshots for the bundled story guests. The native probe uses a fixed tool-call prefix and follows the decoder's selected IDs through the circuit's response and return to Bonsai. The Python verifier compares its trace with the independent interpreter.

This prototype accepts one token at a time in sequence zero with a fully offloaded Bonsai decoder on one NVIDIA GPU. The checked-in NVRTC helper targets SM 6.1. Each context owns its circuit state. A named `llama_qwenpu_forward_reset` restores a firmware snapshot and preserves the circuit's lag history from prefill. A null name clears state and history. Use a fresh context for each independent run. Context serialization covers Bonsai's memory, and the probe uses that serialization to compare the cache during chip-only runs. Circuit-state serialization, context resume, batched decoding, alternate architectures and unconstrained tool-call generation are outside this fixture.
